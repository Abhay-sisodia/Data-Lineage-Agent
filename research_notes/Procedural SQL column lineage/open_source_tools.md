# Open-source lineage tools and libraries: what each does for PROCEDURAL SQL at column level

Method note: as of 2026-10-16, facts marked "(code)" come from reading shallow clones of the default branch: OpenLineage, DataHub, OpenMetadata, sqllineage, SQLGlot, sqlparser-rs, tokern/data-lineage, flowscope, sqlparser-plpgsql and pg-lineage. Stars, licences and push dates come from the GitHub REST API on 2026-10-16. Release dates come from PyPI, Maven Central and GitHub Releases. Nothing was executed against real procedures, so behaviour claims come from reading the code, not from running it.

## Q1. Does any maintained, permissively licensed open-source tool derive column lineage from stored-procedure / function / trigger bodies, especially PL/pgSQL?

### Takeaway
No maintained, permissively licensed tool does real procedural semantics for PL/pgSQL. That means variables, `SELECT INTO`, `RETURN QUERY`/`RETURN NEXT`, OUT parameters, `NEW.x :=`, or `EXECUTE` of constant text. The tools that "handle stored procedures" all do the same shallow thing. They split the body into statements, analyse each DML statement on its own, and union the edges. Control flow, variables and dynamic SQL are dropped. Today only DataHub (MSSQL, column-level, via SQLGlot) and sqllineage (T-SQL, Oracle and BigQuery `CREATE PROCEDURE` only) do this in open source. The only tools that claim deep procedural or dynamic-SQL lineage, Gudu SQLFlow/GSP and QiVo Studio, are not open source.

### Cited Findings
- **Handles stored-procedure bodies, column level: DataHub.** `parse_procedure_code()` calls `split_statements()` on the procedure text. It sorts the pieces into DML statements and `CALL`/`EXEC` procedure calls. Each DML statement is fed separately to `SqlParsingAggregator` (built on SQLGlot) as an `ObservedQuery`, and all of them share one `session_id` so temp tables resolve across statements (code) — [lineage.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/stored_procedures/lineage.py)
- DataHub's procedure result `DataJobInputOutputClass` carries `fineGrainedLineages`, so procedure lineage is column-level (code) — [datajob.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/sql_parsing/datajob.py)
- DataHub's MSSQL docs say procedure lineage comes from static analysis of the definitions. They also say dynamic SQL (`EXEC`, `sp_executesql`) "cannot have dependencies reliably extracted", and that temp/staging tables matching `%#%` are filtered out — [DataHub MSSQL source docs](https://docs.datahub.com/docs/generated/ingestion/sources/mssql)
- **DataHub on PostgreSQL: PL/pgSQL bodies are effectively not analysed.** The Postgres source reads only `pg_proc` rows with `prokind = 'p'`, so it gets procedures but not functions or triggers. It takes `prosrc` as the definition and sets `language=row.language.upper()` (code) — [postgres/source.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/postgres/source.py). `generate_procedure_lineage()` parses only `if procedure.procedure_definition and procedure.language == QueryLanguageClass.SQL` (code) — [stored_procedures/base.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/stored_procedures/base.py). So a `LANGUAGE plpgsql` procedure becomes `"PLPGSQL"`, which is not `SQL`, and gets no parsed lineage. This conclusion comes from reading the code; it was not tested by running it.
- **Handles stored-procedure bodies, column level: sqllineage (since v1.5.8, 2026-05-16).** The changelog says "Preliminary support for parsing stored procedures (#643)" — [changelog.rst](https://github.com/reata/sqllineage/blob/master/docs/release_note/changelog.rst); PRs [#767](https://github.com/reata/sqllineage/pull/767) and [#761](https://github.com/reata/sqllineage/pull/761). `ProcedureExtractor` handles only the sqlfluff segment `create_procedure_statement`. It calls `recursive_crawl("statement")` and merges the per-statement lineage holders, so there is no variable or control-flow semantics (code) — [procedure.py](https://github.com/reata/sqllineage/blob/master/sqllineage/core/parser/sqlfluff/extractors/procedure.py)
- sqllineage's procedure tests (table and column) cover only the dialects `bigquery`, `oracle` and `tsql`. PostgreSQL is not one of them (code) — [test_column_procedure_dialect_specific.py](https://github.com/reata/sqllineage/blob/master/tests/sql/column/test_column_procedure_dialect_specific.py)
- sqllineage sends `create_function_statement` to the `NoopExtractor`, so `CREATE FUNCTION` produces empty lineage (code) — [noop.py](https://github.com/reata/sqllineage/blob/master/sqllineage/core/parser/sqlfluff/extractors/noop.py). These issues are still open: [#446 "CREATE FUNCTION / TABLE FUNCTION support"](https://github.com/reata/sqllineage/issues/446) (2023) and [#703 "Support Table Function in PostgreSQL"](https://github.com/reata/sqllineage/issues/703) (2025).
- **OpenMetadata stored-procedure lineage comes from the query log, not from the body.** The `StoredProcedureLineageMixin` docstring describes the flow: "List Stored Procedures → … Get the queries related to the Stored Procedures in the last X days → Ingest the Lineage". It reads executed child queries from query history (code) — [stored_procedures_mixin.py](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/source/database/stored_procedures_mixin.py). Only the `mssql`, `redshift` and `snowflake` lineage sources use this mixin. The Postgres lineage source does not (code, grep of `ingestion/src/metadata/ingestion/source/database`). Redshift, for example, reads `SVL_STORED_PROC_CALL` / `SYS_PROCEDURE_CALL` — [redshift/queries.py](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/source/database/redshift/queries.py)
- OpenMetadata's Postgres connector does ingest procedures (`prokind='p'`) and functions (`prokind='f'`) as entities, keeping `prosrc` as the definition. It does not derive lineage from that definition (code) — [postgres/queries.py](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/source/database/postgres/queries.py)
- **Not open source but claims deep procedural lineage: Gudu SQLFlow / GSP.** The python_data_lineage README says the bundled Java library is "free for non-commercial use", is limited to SQL "with a length of up to 10k", supports stored procedures, and shows a "Postgres stored procedure" dynamic-SQL example — [python_data_lineage README](https://github.com/sqlparser/python_data_lineage). The GitHub API reports no licence (`None`) for that repo — [repo](https://github.com/sqlparser/python_data_lineage). GSP is described as a "commercial Java library", and pricing "starts from $587.88 for a 1 User Premium License subscription" — [dpriver blog](https://www.dpriver.com/blog/gsp-vs-jsqlparser-vs-sqlglot-sql-parser-comparison-2026/), [ComponentSource](https://www.componentsource.com/product/gudu-sql-flow/prices?pf=new). These pages are vendor or reseller marketing.
- **Not open source: QiVo Studio (Oracle PL/SQL).** It claims "column-level lineage across … packages, procedures, functions, triggers" and "Dynamic SQL resolved, not ignored: built from constants, CASE/DECODE branches, control tables, call sites". Its README says it "is free to use under its licence agreement; it is not open source" — [qivo-studio README](https://github.com/qivo-studio/qivo-studio). These are marketing claims and were not verified.

### Inferences
- The industry baseline for procedure lineage is: split the body, analyse each statement, union the edges, and give up on dynamic SQL. Our desugar-rule layer already goes further than DataHub and sqllineage for PL/pgSQL. Neither tool can be used as a drop-in replacement for the semantics layer.
- DataHub's procedure code is still worth copying for two things: (a) shared-session temp-table resolution across the statements of one routine, and (b) recording `CALL`/`EXEC` as routine-to-routine (`inputDatajobs`) edges instead of dropping them.

### Gaps
- I did not run DataHub against a real `LANGUAGE plpgsql` procedure to confirm empirically that it produces no lineage. The conclusion rests on the `language == SQL` guard in the code.
- I could not check what Gudu GSP's PL/pgSQL support actually does without a licence.

## Q2. Per-tool rows: lineage platforms and metadata catalogs

### Takeaway
The catalogs (OpenLineage/Marquez, Atlas, Egeria, Amundsen, Spline) store and transport lineage; they do not derive it from procedure code. The one thing worth reusing from them is OpenLineage's `ColumnLineageDatasetFacet`, a useful output vocabulary that distinguishes DIRECT from INDIRECT edges. Two maintenance surprises: Amundsen was archived in September 2026, and OpenMetadata's `ingestion/` package is no longer Apache-2.0.

### Inferences
- OpenLineage's facet types (DIRECT/INDIRECT plus subtypes) map closely onto our value / filter / influence flow kinds. Emitting OpenLineage events is a cheap way to interoperate with Marquez, DataHub and OpenMetadata without changing our core.
- OpenMetadata's ingestion code (and `collate-sqllineage`'s packaging) should be checked for licence before anyone copies from it. Copying ideas is fine; copying code is subject to the Collate Community License for `ingestion/`.
- A query-log approach like OpenMetadata's, using `pg_stat_statements` or `auto_explain` with `log_nested_statements`, could act as a dynamic oracle for `EXECUTE`-built SQL that static analysis refuses. That is a technique to borrow, not a component to adopt.

### Gaps
- I did not confirm the exact date or commit when OpenMetadata's `ingestion/` licence changed; this was a shallow clone with no history.
- I did not inspect Atlas or Egeria source for any SQL-routine parser. Their "no procedural parsing" rows rest on their architecture (hooks and metadata exchange), not on a code grep.
- I did not check Spline's code; it is described from its known Spark focus and only noted briefly.

## Q3. Per-tool rows: SQL parsers / lineage libraries and their procedural AST support

### Takeaway
Every open-source multi-dialect parser treats a PostgreSQL function body as an opaque string literal. That covers sqlparser-rs, SQLGlot, JSqlParser, sqlfluff and pgsql-ast-parser. Only the libpg_query family (`pg_query_parse_plpgsql`) yields a real PL/pgSQL AST, which is what we already use. That includes pglast, which is GPL-3.0-or-later and needs a licence flag. SQLGlot has procedural block nodes only for T-SQL and Trino. Calcite and ZetaSQL/GoogleSQL have strong single-statement column provenance or scripting machinery, but neither applies to PL/pgSQL.

### Cited Findings
- **sqlparser-rs (apache/datafusion-sqlparser-rs).** For PostgreSQL, `CREATE FUNCTION … AS $$…$$` is parsed by `parse_create_function_body_string`, which stores the body as `Expr::Value(Value::DollarQuotedString(s))`, an unparsed string (code) — [parser/mod.rs](https://github.com/apache/datafusion-sqlparser-rs/blob/main/src/parser/mod.rs). The AST does have `Statement::CreateProcedure { body: ConditionalStatements }`, `BeginEndStatements`, `RaiseStatement` and `Return(ReturnStatement)` for dialects with inline procedural bodies such as MSSQL (code) — [ast/mod.rs](https://github.com/apache/datafusion-sqlparser-rs/blob/main/src/ast/mod.rs). I found no `ATOMIC` handling in the parser (code grep). Apache-2.0, Rust, 3,466 stars, pushed 2026-10-15; latest changelog file is 0.63.0.
- **sqlparser-plpgsql (new add-on, found by GitHub search).** "PL/pgSQL scanning, preprocessing, and body parsing for sqlparser-rs". Its `PlPgSqlPreprocessor` "rewrites a whole body into shapes a SQL parser accepts, turning `:=` assignments into `SET`, lifting `DECLARE` defaults into a context, and folding `SELECT INTO` into scalar subq[ueries]" — [README](https://github.com/LucaCappelletti94/sqlparser-plpgsql). MIT, Rust, version 0.1.0, about 2.5k lines, depends on sqlparser-rs `main`; last commit 2026-10-01 (code); 0 stars.
- **SQLGlot.** The Postgres tokenizer treats `$…$` as `HEREDOC_STRING` (code) — [dialects/postgres.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/dialects/postgres.py). Procedural nodes `StoredProcedure`, `Block`, `IfBlock` and `WhileBlock` exist in [expressions/query.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/expressions/query.py), but they are produced only by the T-SQL parser ([parsers/tsql.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/parsers/tsql.py)) and the Trino routine parser (`_parse_routine_if`, `_parse_routine_while` in [parsers/trino.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/parsers/trino.py)) (code). There is no "plpgsql" string anywhere in the package (code grep). `sqlglot.lineage.lineage(column, sql, schema, sources=…)` works over a query; its `sources` mapping "will be used to continue building lineage", which is how callers chain statements — [lineage.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/lineage.py). MIT; PyPI 30.23.0 on 2026-10-14; 9,686 stars.
- **sqllineage.** Built on sqlfluff (and sqlparse); see Q1 for procedure support. MIT; PyPI 1.5.9 on 2026-09-05; last commit 2026-10-14; 1,679 stars — [repo](https://github.com/reata/sqllineage)
- **sqlfluff.** Parser and linter only; no lineage. sqllineage's dependency on its `create_procedure_statement` / `create_function_statement` segments shows that it parses those statements' shells (code above). MIT; PyPI 4.4.0 on 2026-10-02; 9,978 stars.
- **libpg_query.** Exposes `pg_query_parse_plpgsql()`, which returns `PLpgSQL_function` JSON (`datums`, `PLpgSQL_stmt_block`, `PLpgSQL_stmt_if`, …) for `CREATE FUNCTION … LANGUAGE plpgsql`. Licence: PostgreSQL licence for the PG server sources, "All other parts … 3-clause BSD" — [libpg_query README](https://github.com/pganalyze/libpg_query). 1,485 stars; pushed 2026-10-02.
- **pglast (Python binding to libpg_query).** **Licence: "GNU General Public License version 3 or later"** — [pglast README](https://github.com/lelit/pglast); PyPI metadata `GPL-3.0-or-later`; PyPI 8.6 on 2026-10-14; 404 stars.
- **JSqlParser.** `CreateFunction` is built from `List<String> functionDeclarationParts`, so the body is kept as raw token strings, not an AST (code) — [CreateFunction.java](https://github.com/JSQLParser/JSqlParser/blob/master/src/main/java/net/sf/jsqlparser/statement/create/function/CreateFunction.java). Dual LGPL-2.1 / Apache-2.0. The README points to JSQLTranspiler (Starlake.ai) for "column resolution and lineage" — [README](https://github.com/JSQLParser/JSqlParser). Release jsqlparser-5.4 on 2026-09-13; 5,965 stars.
- **Apache Calcite.** `RelMdColumnOrigins` implements `getColumnOrigins()` over relational-algebra nodes (Aggregate, Join, SetOp, Project, Calc, TableScan, Filter, Sort, TableModify, Exchange, Sample, Snapshot, TableFunctionScan). It works on `RelNode` plans, not procedural code — [Javadoc](https://calcite.apache.org/javadocAggregate/org/apache/calcite/rel/metadata/RelMdColumnOrigins.html). Apache-2.0; Maven `calcite-core` release 1.42.0 (metadata updated 2026-05-31) — [Maven](https://repo1.maven.org/maven2/org/apache/calcite/calcite-core/maven-metadata.xml); 5,193 stars.
- **ZetaSQL → GoogleSQL (repo renamed to google/googlesql).** It has a `googlesql/scripting` package containing `control_flow_graph.{h,cc}`, `parsed_script.{h,cc}`, `script_executor*`, `procedure_extension.proto`, `variable.proto` and `stack_frame.h` (GitHub contents API) — [googlesql/scripting](https://github.com/google/googlesql/tree/master/googlesql/scripting). It covers GoogleSQL (BigQuery-style) scripting, not PL/pgSQL. Apache-2.0, C++; release 2026.10.1 on 2026-10-07; 2,641 stars.
- **pgsql-ast-parser.** The README has no PL/pgSQL or function-body parsing section (README grep). GitHub API licence `None`. Last push 2026-01-27; 346 stars — [repo](https://github.com/oguimbal/pgsql-ast-parser)
- **SQLMesh.** Column lineage uses `sqlglot.lineage.lineage` together with `build_scope` and `qualify`, applied to model queries — [sqlmesh.core.lineage docs](https://sqlmesh.readthedocs.io/en/latest/_readthedocs/html/sqlmesh/core/lineage.html). No routine support. Apache-2.0; PyPI 0.236.3 on 2026-10-06; 3,323 stars (repo now `SQLMesh/sqlmesh`).
- **dbt column lineage (open source).** `dbt-colibri` (MIT; PyPI 0.3.7 on 2026-10-05) uses "SQLGlot for SQL parsing and column lineage extraction" over dbt models — [README](https://github.com/b-ned/dbt-colibri). `dbt-column-lineage` (Oisix; MIT; PyPI 0.6.8 on 2026-09-25) builds lineage "of dbt models" from `manifest.json` / `catalog.json` — [README](https://github.com/Oisix/dbt-column-lineage). Both cover models (SELECTs) only.
- **Datafold data-diff.** Archived (GitHub API `archived: true`); last push 2024-05-17; PyPI 0.11.2 on 2024-05-17; MIT — [repo](https://github.com/datafold/data-diff). This is a diffing tool, not a lineage tool.

### Inferences
- pglast's GPL-3.0-or-later licence matters if the product is to be "permissively licensed" and distributed. The permissive path to the same capability is libpg_query (BSD-3) through a thin binding of our own. Another option is a permissively licensed binding such as the Rust `pg_query` crate, but I did not verify its licence this session.
- sqlparser-plpgsql's preprocessing idea is close to our desugar rules, implemented as a generic rewrite: `:=` becomes `SET`, `SELECT INTO` becomes a scalar subquery, and `DECLARE` becomes a context. It is too young (v0.1.0, 0 stars) to depend on, but it is a useful technique reference.
- GoogleSQL's `control_flow_graph` for scripts is the closest open-source example of a principled CFG over procedural SQL. Its design could guide a dataflow (reaching-definitions) pass over the PL/pgSQL AST, replacing one-rule-per-form desugaring.
- Calcite's `getColumnOrigins` could serve as a second single-statement oracle (via a JVM sidecar) to cross-check SQLGlot results on the desugared statements. It does not help with routine semantics.

### Gaps
- I did not verify whether sqlparser-rs parses PostgreSQL `BEGIN ATOMIC` SQL-standard bodies; the grep for `ATOMIC` in the parser found nothing.
- I did not check the licence and maintenance of other libpg_query bindings: the Rust `pg_query` crate, Go `pg_query_go`, Ruby `pg_query`, and .NET `pgsqlparser-dotnet` (found by search, MIT, pushed 2026-10-09).
- I did not find or confirm whether dbt Cloud Explorer's column lineage is open source. It is a dbt Labs SaaS feature and was not researched here.

## Q4. GitHub search: repositories doing lineage from PL/pgSQL, PL/SQL or T-SQL procedures

### Takeaway
Searching GitHub for "plpgsql lineage" returned 0 repositories. Procedure-lineage repositories are almost all tiny hobby or demo projects (0–25 stars), mostly T-SQL, often with no licence, and several are LLM-based (out of scope). Two have real 2026 activity and some technical interest: FlowScope (Apache-2.0, Rust, sqlparser-rs) and pg-lineage (a PG/Oracle procedure field-lineage script, no licence). FlowScope only labels CREATE FUNCTION/PROCEDURE statements; pg-lineage is regex plus SQLGlot.

- **1999mxy/pg-lineage.** "PostgreSQL / Oracle / TDSQL stored procedure (PROCEDURE / FUNCTION) field-level lineage", including recursion into procedures that create referenced temp tables — [README](https://github.com/1999mxy/pg-lineage). ### Inferences
- There is no community-maintained open-source PL/pgSQL routine-lineage engine to adopt. Our routine-semantics layer is effectively novel work in open source. The useful outside inputs are techniques: DataHub's shared-session splitting, sqlparser-plpgsql's rewrites, GoogleSQL's script control-flow graph, OpenMetadata's query-log oracle, and OpenLineage's facet vocabulary.
- The one feature only commercial tools (Gudu, QiVo) claim is resolving dynamic SQL from constants, branches and control tables. QiVo's description ("built from constants, CASE/DECODE branches, control tables, call sites") reads like a string-constant-propagation design worth matching for `EXECUTE` of constant or near-constant text.

### Gaps
- GitHub search results are ranked by stars and capped at 12 per query. Unstarred but relevant repositories may have been missed, and code search (as opposed to repository search) was not run.
