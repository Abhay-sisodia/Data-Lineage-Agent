# Build the routine IR, let PostgreSQL judge it

No open-source tool, paper or repository found by this research computes column lineage through PL/pgSQL routines and psql scripts with real procedural semantics. That means none tracks variables, `SELECT INTO`, `RETURN NEXT`, OUT rows, `NEW.x :=` or `EXECUTE`. So there is nothing to drop in for your desugar layer, and the fix has to be an architecture change rather than a dependency. The open-source tools that "handle stored procedures" (DataHub, sqllineage) split the body into statements, analyse each one alone and union the edges. DataHub skips `LANGUAGE plpgsql` bodies entirely on PostgreSQL. The commercial leaders either document "not processed" for dynamic SQL (IBM Manta) or make unverified marketing claims (Gudu GSP). Two things replace one-rule-per-form desugaring. The first is a small SSA-style intermediate representation (IR) lowered from the libpg_query PL/pgSQL tree, with one generic dataflow pass over it; the academic literature (Tübingen's PL/SQL compiler, Froid, the program-slicing work on database state) supplies that design. The second is PostgreSQL 17 itself, used as both the per-statement semantic engine and the oracle. Local experiments on your PG17.11 confirmed that `auto_explain` logs the post-`format()` text of dynamic SQL, `pg_depend` records column-level dependencies for `BEGIN ATOMIC` bodies, `plpgsql_check` resolves tables inside constant dynamic SQL, and `psql -e` echoes `\gset`/`:'var'` substitutions. Nobody has solved non-constant dynamic SQL, static psql-variable semantics, or published a lineage-labelled procedural benchmark, so you must build those. Two licence risks need action: **pglast is GPL-3.0-or-later** while the libpg_query underneath it is BSD-3, and **OpenMetadata's `ingestion/` package is now under the Collate Community License**, not Apache-2.0.

## Every tool stops at "split the body, parse each statement"

The open-source baseline is shallower than your current layer. DataHub's `parse_procedure_code()` splits procedure text and feeds each DML statement to its SQLGlot-based aggregator under a shared `session_id`, so temp tables resolve across statements, and it emits column-level `fineGrainedLineages` ([lineage.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/stored_procedures/lineage.py)). On PostgreSQL, though, the source reads only `prokind='p'` rows, and procedure lineage is parsed only when the language equals `SQL` ([postgres/source.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/postgres/source.py), [stored_procedures/base.py](https://github.com/datahub-project/datahub/blob/master/metadata-ingestion/src/datahub/ingestion/source/sql/stored_procedures/base.py)). By code reading, therefore, **a PL/pgSQL procedure gets no parsed lineage and functions and triggers are never read**. DataHub's own SQL-parsing page lists multi-statement scripts, stored procedures and UDFs as unsupported. It does claim "97-99% accuracy", but that figure covers single statements only ([DataHub SQL parsing](https://docs.datahub.com/docs/lineage/sql_parsing)). sqllineage added "preliminary" procedure support in v1.5.8 (May 2026). It works the same split-and-merge way, is tested only on T-SQL, Oracle and BigQuery, and routes `CREATE FUNCTION` to a no-op extractor ([procedure.py](https://github.com/reata/sqllineage/blob/master/sqllineage/core/parser/sqlfluff/extractors/procedure.py), [noop.py](https://github.com/reata/sqllineage/blob/master/sqllineage/core/parser/sqlfluff/extractors/noop.py)). OpenMetadata derives procedure lineage from query history, not from the body, and only for MSSQL, Redshift and Snowflake. Its Postgres connector catalogues `prosrc` without lineage ([stored_procedures_mixin.py](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/source/database/stored_procedures_mixin.py)). The OpenLineage SQL visitor has no function, procedure or trigger arm at all ([visitor.rs](https://github.com/OpenLineage/OpenLineage/blob/main/integration/sql/impl/src/visitor.rs)). These are code-reading conclusions; none of these tools was run against a real PL/pgSQL routine.

Parsers fare no better. sqlparser-rs stores a PostgreSQL `$$` body as an unparsed `DollarQuotedString` ([parser/mod.rs](https://github.com/apache/datafusion-sqlparser-rs/blob/main/src/parser/mod.rs)). SQLGlot tokenises it as a heredoc string and builds procedural `Block`/`IfBlock` nodes only for T-SQL and Trino; the string "plpgsql" does not occur in the package ([dialects/postgres.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/dialects/postgres.py), [parsers/trino.py](https://github.com/tobymao/sqlglot/blob/main/sqlglot/parsers/trino.py)). JSqlParser keeps function bodies as token strings ([CreateFunction.java](https://github.com/JSQLParser/JSqlParser/blob/master/src/main/java/net/sf/jsqlparser/statement/create/function/CreateFunction.java)). The vendor-written Gudu benchmark says SQLGlot "handles PL/pgSQL RETURN QUERY" ([dpriver comparison](https://www.dpriver.com/blog/gsp-vs-jsqlparser-vs-sqlglot-sql-parser-comparison-2026/)). That is a parse-success claim and is consistent with the body surviving as an opaque string, not with any procedural analysis. **Only the libpg_query family (`pg_query_parse_plpgsql`) produces a real PL/pgSQL tree**, and you already use it.

A GitHub repository search for "plpgsql lineage" on 2026-10-16 returned **zero** results. "stored procedure lineage" returned 21, the best with 25 stars, mostly T-SQL hobby projects, some unlicensed and several LLM-based. The two 2026-active projects are thin. pg-lineage is a roughly 1,100-line regex-plus-SQLGlot script with no licence ([repo](https://github.com/1999mxy/pg-lineage)). FlowScope only labels `CREATE FUNCTION` statements and has Apache-2.0 core code but an "O'Saasy" licence on its app ([repo](https://github.com/pondpilot/flowscope)). The only new component with real PL/pgSQL intent is sqlparser-plpgsql (MIT, Rust, v0.1.0, 0 stars). Its preprocessor rewrites `:=` to `SET`, lifts `DECLARE` defaults into a context and folds `SELECT INTO` into scalar subqueries ([README](https://github.com/LucaCappelletti94/sqlparser-plpgsql)). It is a generic version of your desugar rules, worth reading as a technique and too young to depend on.

Commercial vendors confirm the gap rather than fill it. IBM's Manta-based product documents PostgreSQL support for "Functions (SQL and PL/pgSQL)", with no triggers or procedures listed and no mention of column level. It states verbatim that assets using `EXECUTE` dynamic code "are not processed" ([IBM Docs](https://www.ibm.com/docs/en/DSXDOC/wsj/lineage/lineage-postgresql.html)). Its architecture, per an ICSE 2024 talk, is per-language scanners lowering code into a data-flow graph analysed by "modular symbolic data flow analysis" ([ICSE 2024 SEIP](https://conf.researchr.org/details/icse-2024/icse-2024-software-engineering-in-practice/28/Data-Lineage-Analysis-for-Enterprise-Applications-by-Manta-The-Story-of-Java-and-C-)). That is the IR-plus-analysis pattern, not rule-per-form. Gudu claims GSP parses the full procedural language, resolves `%TYPE` and temp tables from `SELECT INTO`, and handles `EXECUTE format()`, but publishes no accuracy numbers ([Gudu blog](https://www.dpriver.com/blog/?p=3177)). Dataedo, Ataccama and Collibra document that dynamic SQL is excluded ([Dataedo PL/SQL](https://docs.dataedo.com/data-sources/sql-parser/plsql-parsing), [Ataccama](https://docs.ataccama.com/one/16.1.0/lineage/oracle-lineage-scanner.html)). Microsoft Purview, Snowflake, Databricks and Dataplex capture procedure lineage at runtime and still exclude functions, triggers, temp tables or routines ([Purview](https://learn.microsoft.com/en-us/purview/register-scan-azure-sql-database), [Snowflake Access History](https://docs.snowflake.com/en/user-guide/access-history), [Dataplex](https://cloud.google.com/dataplex/docs/about-data-lineage)). **No vendor or paper publishes procedural-lineage recall**, so your 77% blind-holdout figure has no public comparator.

## Your desugar forms collapse into eight IR primitives

The literature does not offer a component, but it does offer a principled design. The Tübingen line (Duta, Hirn and Grust, CIDR 2020, and successors) lowers PL/pgSQL to **SSA, so that "the diversity of PL/SQL control flow constructs" becomes a single `goto` primitive**, then to ANF, then to `WITH RECURSIVE`. Throughout, embedded SQL expressions and queries stay as parameterised black boxes ([CIDR 2020](https://www.vldb.org/cidrdb/papers/2020/p1-duta-cidr20.pdf)). Microsoft's Froid inlines a T-SQL UDF by chaining each statement as a derived table through Apply, with variables as columns ([arXiv 1712.00498](https://arxiv.org/pdf/1712.00498)). The program-slicing work on database programs adds the missing piece: Willmor, Embury and Shao extend the dependence graph with program-to-database and database-to-database dependencies ([ICSM 2004](https://orca.cardiff.ac.uk/id/eprint/45517/)), and Halder and Cortesi give them a semantics ([thesis](https://iris.unive.it/retrieve/34227e8d-14b2-428b-9d88-ede5a5685deb/thesisHalder.pdf)). Treat every table column as a global variable that DML defines and queries use, and trigger and procedure effects become ordinary def-use edges.

Whole-routine inlining cannot be the mechanism, and the papers say so themselves. Froid disabled loops, and it handled only **59.8% of 85,329 real scalar UDFs** ([arXiv 1712.00498](https://arxiv.org/pdf/1712.00498)). Hirn's 2024 thesis lists dynamic SQL, exception handling, INSERT/UPDATE/DELETE and DDL as unsupported ([thesis](https://db.cs.uni-tuebingen.de/publications/2024/new-compilation-methods-for-complex-user-defined-functions/dissertation_hirn_denis.pdf)). Gupta and Ramachandra found DML and exception handling "fairly common in stored procedures" across Azure SQL workloads ([PVLDB 14(8)](https://www.vldb.org/pvldb/vol14/p1378-ramachandra.pdf)). Your hardest forms are exactly these side-effecting ones. A lineage analyser, however, needs only a sound over-approximation of dependencies, not semantic equivalence. So it can absorb what the compilers reject: DML becomes an effect edge, an exception handler becomes an extra control-flow successor, a cursor becomes a query-bind inside a loop, and dynamic SQL becomes string analysis plus a fallback. **Adopt their intermediate forms, not their output.**

The resulting IR is small. It has `assign` (x := SQL expression), `bind` (x1..xn := query, which covers SELECT INTO, FETCH, FOR-over-query and GET DIAGNOSTICS), `emit` (append to the routine result: RETURN, RETURN NEXT, RETURN QUERY, OUT/INOUT, BEFORE-trigger `NEW`, the final ATOMIC SELECT), `effect` (table.col ⊇ query: INSERT/UPDATE/DELETE/MERGE/COPY), `call`, `dyn`, `branch` (which carries filter dependencies) and `opaque` (conservative edges plus an explicit unknown). One monotone pass then computes lineage. Each abstract value is a set of (source column, flow kind) pairs, unioned at merge points, so loops reach a fixpoint quickly. This is Müller and Grust's "query as its own interpreter, values replaced by dependency sets", applied statically ([arXiv 1805.11517](https://arxiv.org/abs/1805.11517)). Tomingas et al.'s split of transformation weight from filter weight ([KDIR 2016](https://www.scitepress.org/PublishedPapers/2016/60543/60543.pdf)) and OpenLineage's DIRECT/INDIRECT subtypes map onto your value/filter/influence kinds. Under this design a new syntactic form needs one lowering, not a new lineage rule. The table below maps your current rules onto it.

| Current desugar rule | IR lowering | Where the facts come from | Oracle |
|---|---|---|---|
| RETURN QUERY EXECUTE of constant `format()` | `dyn` → constant-propagate, evaluate string on PG17, parse result | `PLpgSQL_stmt_return_query.dynquery` is an expression, not SQL (verified) | plpgsql_check dependencies; auto_explain query text |
| RETURN NEXT of records | `emit` of record whose fields were `assign`ed | `PLpgSQL_recfield` datums; `retvarno` is **not emitted** in JSON, so read the variable from the expression text | plpgsql_check tracer (field-by-field values verified) |
| OUT/INOUT functions in FROM/LATERAL | routine summary: output column → input sets; `call` at use site | `pg_proc.proargmodes/proargnames/proallargtypes` (verified); OUT row is the `PLpgSQL_row` with `lineno: -1` | — |
| `NEW.x :=` in triggers | `assign` to recfield of NEW; trigger `emit` into target row | Trigger JSON gives NEW/OLD recs and `new.label` row fields (verified) | Tracer shows NEW before/after (verified) |
| BEGIN ATOMIC bodies | Read pre-split, fully qualified body from catalog | `pg_get_function_sqlbody` (verified) | `pg_depend` column set (verified) |
| SELECT INTO several targets | `bind` with positional varno row | INTO clause blanked in query text, target row lists varnos (verified) | auto_explain |
| Constant dynamic SQL | Same as `dyn` | Server-side folding (below) | plpgsql_check, auto_explain |
| psql `\gset` / `:'var'` | Script-level `bind` of client variables, then substitution | Run real `psql -e` on scratch DB (verified) | Echoed stream |
| COPY FROM STDIN | `effect` with a literal source node | Statement text; `log_statement` | test_decoding |

Dynamic SQL gets a three-tier treatment taken from the string-analysis literature. Tier one is exact constant folding. PG17 marks `quote_ident`, `quote_literal(text)` and `textcat` as immutable and `format` and `concat` as stable (verified via `pg_proc.provolatile`). So when every free variable of a `dynquery` expression is constant in the IR, the live server can evaluate `SELECT <expr>` exactly, with an allow-list of function OIDs to keep it side-effect-free. Tier two is finite enumeration: when a table name ranges over IF branches or an array literal, enumerate the candidates and intersect them with the catalog, as Christensen, Møller and Schwartzbach's regular approximation ([SAS 2003](https://cs.au.dk/~amoeller/papers/strings/)) and Gould, Su and Devanbu's schema-aware check ([ICSE 2004](https://www.cs.ucdavis.edu/~su/icse.pdf)) suggest. Tier three is a typed "unresolved dynamic SQL" boundary with conservative influence edges, matching how Dataedo and IBM surface the gap instead of dropping it silently.

## PostgreSQL 17 already computes the semantics you hand-code

The researchers verified locally exactly what libpg_query's PL/pgSQL JSON gives and withholds. It runs with no catalog, so `%TYPE` remains the literal string `"src.amt%TYPE"`. It omits `retvarno`, `out_param_varno`, `fn_rettype`/`fn_retset`, `rectypeid` and type OIDs ([pg_query_json_plpgsql.c](https://github.com/pganalyze/libpg_query/blob/17-latest/src/pg_query_json_plpgsql.c)). It drops zero-valued integers, so consumers must default a missing `dno` or `recparentno` to 0. And **`r tgt%ROWTYPE; r.id := 1;` fails with `"r.id" is not a known variable`**; this is one of the forms that broke your holdout. Declaring the variable as `record` parses fine, so the workaround is a textual rewrite of `%ROWTYPE` declarations to `record`, with the real row type kept in your own symbol table and filled from the catalog. Types, row shapes and OUT signatures should come from `pg_proc` and the catalog, never from text inference.

For each embedded statement, PostgreSQL's analyser can replace hand-written resolution of `*`, `USING`, aliases, views and INSERT column mapping. Substitute PL/pgSQL variables with `$n`, which is what PL/pgSQL itself does, and run `EXPLAIN (VERBOSE, COSTS OFF, GENERIC_PLAN)` (PG16+). The local test showed every column qualified, and the INSERT child output in target-attnum order with `NULL::numeric` for omitted columns, so INSERT mapping is recoverable by position ([PG17 EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)). Two caveats were verified. UPDATE subplans do not label the target column (`"Output": ["(s.amt * $1)", "tgt.ctid", "s.ctid"]`). And plans are plan-shaped: outputs get pushed down or reordered. The richer artefact is the analysed Query tree from `debug_print_rewritten`. It carries `resorigtbl/resorigcol` and per-relation `selectedCols/insertedCols/updatedCols` bitmaps ([PG17 logging](https://www.postgresql.org/docs/17/runtime-config-logging.html)), but needs a reader for the `nodeToString` format. RowDescription's `PQftable/PQftablecol` gives origins only for bare column references; expressions, UNION and set-returning functions yield 0, and view columns map to the view ([protocol docs](https://www.postgresql.org/docs/17/protocol-message-formats.html)). That makes it a pass-through check, not lineage. **None of these facilities models data flow *between* statements.** PostgreSQL supplies exact per-statement transfer functions; your IR composes them.

The catalog is a free, exact ground-truth set for part of the corpus. For a `BEGIN ATOMIC` function, `pg_depend` held one row per column touched, and `routine_column_usage` returned the same set. For the INSERT/UPDATE variant it included target columns without distinguishing read from written. A quoted `LANGUAGE sql` body produced only a namespace dependency ([PG17 routine_column_usage](https://www.postgresql.org/docs/17/infoschema-routine-column-usage.html)). This is an unordered set per object, with no output-to-input mapping. It therefore validates lineage ("every claimed column is in the set; every set member is explained") but cannot produce it. Re-creating quoted SQL bodies as ATOMIC in a scratch database upgrades them for analysis, except for polymorphic signatures ([CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html)).

plpgsql_check is the strongest static oracle for PL/pgSQL specifically. It is MIT-licensed, packaged by PGDG as 2.10.13 for PG17 and supports PG 14–20, but it is not in the stock `postgres:17` image ([README](https://github.com/okbob/plpgsql_check)). Locally, `plpgsql_show_dependency_tb` found the `audit`, `src` and `tgt` relations inside `RETURN QUERY EXECUTE format('…%I', 'audit')` and a constant `EXECUTE`. It returned nothing when the table name was a parameter. Its dependency report is relation-level, not column-level. Its tracer printed `NEW` before and after `NEW.label := upper(NEW.label)`, field-by-field record assembly, and nested trigger frames. That is exactly the evidence for the forms runtime logging cannot see, though it requires superuser rights and execution.

At runtime, auto_explain (`log_nested_statements`, `log_verbose`, JSON, `log_min_duration=0`) is the best "what actually ran" oracle. Both local test runs saw dynamic SQL logged **after substitution**: `EXECUTE format('INSERT INTO %I…', tbl)` appeared as `INSERT INTO tgt2(id,z) SELECT id, a*3 FROM src`, with a `CONTEXT` line naming the function and PL/pgSQL line ([PG17 auto_explain](https://www.postgresql.org/docs/17/auto-explain.html)). The blind spots were verified too. `NEW.x :=`, `r.f :=` and `RETURN NEXT r` are simple expressions and produce no entry. Trigger statements show `NEW` fields folded to constants. Variables appear as constants for the first five calls and as `$n` after the switch to a generic plan. COPY, DDL and DO are utility statements and are not logged. Untaken branches leave no trace. ATOMIC bodies log an empty query text. Rolled-back work is logged with no marker. pg_stat_statements with `track=all` records nested statements (`toplevel=f`) but normalises constants and loses call site and order ([PG17 pg_stat_statements](https://www.postgresql.org/docs/17/pgstatstatements.html)). test_decoding gives committed table writes and omits rollbacks. No published project derives column lineage from auto_explain output, and no maintained PostgreSQL extension emits column lineage from executor hooks. A roughly 300-line `ExecutorStart_hook` extension could add the missing target-column attnums, but it would inherit the same blind spots.

Perturbation runs can generate column-level ground truth: clone a template database, mutate one source column with an injective, order-preserving transform, re-run and diff targets. The researchers found **no published description of this for SQL lineage**. The scheme is sound for positive evidence and incomplete: filters, aggregates, unreached branches and non-injective functions mask changes, and nondeterminism must be frozen. Paired with static analysis, its edges sort cleanly. Edges confirmed by both are verified. Perturbation-only edges are static misses, which auto_explain's `CONTEXT` line can locate. Static-only edges are either unexercised paths or masked mutations.

psql is the one layer where execution is the only practical answer. pgspecial, the BSD library behind pgcli, implements describe commands but not `\set`, `\gset`, `\if` or interpolation ([pgspecial](https://github.com/dbcli/pgspecial)). Running the real `psql -X -e` locally echoed `SELECT "id" FROM "src" WHERE name = 'src' LIMIT 2;` from `:"col"`, `:"tname"`, `:'tname'` and `:n`, and handled inline `COPY … FROM STDIN` ([PG17 psql](https://www.postgresql.org/docs/17/app-psql.html)). The echoed stream is canonical SQL. Its limit is that the script must actually run against a schema with enough seed data for every `\gset` query to return a row.

## Licence and maintenance risks to clear before scaling

The most consequential licence finding concerns your own stack. **pglast is "GNU General Public License version 3 or later"** ([pglast README](https://github.com/lelit/pglast)); the project venv has 8.5 installed. libpg_query, which does all the real work, is 3-clause BSD outside the PostgreSQL-licensed server sources ([libpg_query README](https://github.com/pganalyze/libpg_query)). pglast's `parse_plpgsql` is a one-line `loads(parse_plpgsql_json(...))` (verified in the 8.5 source), so a thin binding of your own over libpg_query removes the GPL exposure at low cost if the framework is ever distributed under a permissive licence. A .NET binding (pgsqlparser-dotnet, MIT) was seen in search. The licences of the Rust `pg_query` crate and the Go binding were not verified.

OpenMetadata's repository root is Apache-2.0, but **`ingestion/LICENSE` is the Collate Community License Agreement 1.0**, which excludes competing SaaS/PaaS use, and PyPI `openmetadata-ingestion` 2.0.5.1 declares it ([ingestion/LICENSE](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/LICENSE)). The date of the change was not established. Copy ideas from it, not code, and check the `collate-sqllineage` packaging before depending on it. Gudu's `python_data_lineage` has no licence on GitHub and is free only for non-commercial use with a 10k-character cap ([README](https://github.com/sqlparser/python_data_lineage)). QiVo Studio is "not open source" ([README](https://github.com/qivo-studio/qivo-studio)). Several smaller items carry their own restrictions:

- FlowScope's `app/` is under the O'Saasy licence.
- pg-lineage and pgsql-ast-parser have no licence, so their code cannot be reused.
- JSqlParser is dual LGPL-2.1/Apache-2.0.
- The Tübingen `flummi` prototype is GPL-3.0, and the PL/SQL-to-SQL compiler itself was not found in public ([DBatUTuebingen](https://github.com/orgs/DBatUTuebingen/repositories)).
- The SQL-ProcBench paper is CC BY-NC-ND; the repository's own licence is unverified, and it was reportedly archived in June 2026 ([PVLDB](https://www.vldb.org/pvldb/vol14/p1378-ramachandra.pdf)).

Several projects are dead: Amundsen was archived in September 2026, tokern/data-lineage (MIT, pglast-based) in 2023, and data-diff in 2024. The extensions you would add are permissive: plpgsql_check and pg_tracing are MIT, and pgaudit and pg_stat_monitor use the PostgreSQL licence. pg_tracing's README lists only PG 14–16 ([pg_tracing](https://github.com/DataDog/pg_tracing)).

## Ranked recommendation

**(1) What replaces or strengthens the routine-semantics layer.** First, build the eight-primitive SSA-style IR described above. Lower it from libpg_query's PL/pgSQL JSON, apply the `%ROWTYPE`-to-`record` pre-rewrite, and run one monotone set-union dataflow pass. A worklist over networkx is enough; pyDatalog (a pure-Python cp311 wheel exists) is an option if you want the rules declarative and auditable. No adoptable component exists, so this is the replacement, designed after Tübingen SSA/ANF, Froid's statement chaining and the database-state dependence graphs. Second, take every type, OUT/INOUT shape, SETOF/TABLE signature and ATOMIC body from the live PG17 catalog (`pg_proc`, `pg_get_function_sqlbody`) instead of inferring them from text. Third, replace the constant-`format()` and constant-dynamic-SQL rules with one constant-propagation pass whose strings are evaluated by the server under a volatility allow-list. Fourth, keep SQLGlot as the per-statement engine with IR variables bound through its `sources` mapping, and use `EXPLAIN (VERBOSE, GENERIC_PLAN)` as a cross-check on embedded statements. Fifth, canonicalise psql scripts by running real `psql -e` against a scratch database. Borrow DataHub's shared-session temp-table resolution and its CALL-as-edge modelling, read sqlparser-plpgsql's rewrites for ideas, and emit OpenLineage `ColumnLineageDatasetFacet` for interoperability. Do not adopt DataHub, sqllineage, OpenLineage, sqlparser-rs or SQLGlot's procedural nodes as the routine layer; none analyses PL/pgSQL.

**(2) What serves as the runtime and catalog oracle.** In rank order:

1. auto_explain (nested, verbose, JSON), joined on routine and line through `CONTEXT`. It covers statement coverage and dynamic-SQL text.
2. `pg_depend` / `routine_column_usage` / `view_column_usage`, the exact column sets for views and ATOMIC bodies.
3. plpgsql_check. It covers relation dependencies including constant dynamic SQL, a catalog compile check of your symbol table, and the tracer for `NEW.x :=` and record-field writes.
4. Perturbation runs over template-database clones, for column-level positive evidence.
5. test_decoding and pg_stat_statements, as cheap write-set and statement-set cross-checks.

ProvSQL (where-provenance, experimental, PG17 untested) and a Gudu GSP trial on your holdouts are optional comparators, not dependencies. Score SQL-ProcBench's PL/pgSQL objects as exact, conservative or refused per routine, as Froid reported coverage. That gives a blind coverage measure free of the bias of your own holdouts.

**(3) What nobody has solved, where you must build.** You must build:

- Def-use or column lineage specifically over PL/pgSQL. No paper and no open-source tool exists; GitHub returns zero repositories.
- Non-constant dynamic SQL. Every vendor documents "not processed", and every compiler declares it out of scope.
- A static psql-variable and `\if` interpreter. None exists in any language that was checked.
- Lineage for simple-expression assignments. These are invisible to every runtime facility, so only static analysis plus the plpgsql_check tracer covers them.
- The libpg_query JSON gaps: the `%ROWTYPE` field-assignment parse error, missing `retvarno` and `out_param_varno`. Work around them or patch upstream.
- Target-column labels for UPDATE in plans.
- A lineage-labelled procedural benchmark. None is public; Microsoft's 1,700-lineage set is unreleased and LLM-oriented ([arXiv 2508.07179](https://arxiv.org/html/2508.07179v1)).

## Conclusion

Your recall decays with every holdout because each rule encodes a *syntax* when it should encode a *meaning*, and PL/pgSQL has far more syntaxes than meanings. The evidence suggests the meanings number about eight (assign, bind, emit, effect, call, dyn, branch, opaque). It also shows the two hardest semantic questions are already answered exactly by the database you run: what a statement's columns resolve to, and what a dynamic string evaluates to. The strategic shift is to stop competing with PostgreSQL's analyser and start interrogating it, while reserving your own code for the one thing no system does: composing statement semantics across a routine's control and data flow.

That reframes the 77% figure. No vendor publishes a procedural recall number, IBM documents dynamic SQL as unprocessed, and the platform owners retreated to runtime capture. A hybrid that labels each edge as static-derived, catalog-confirmed, runtime-observed or perturbation-proven would be ahead of the published state of the art, not catching up to it. It also turns each blind holdout from a list of new rules to write into a list of lowering gaps and oracle disagreements to explain.
