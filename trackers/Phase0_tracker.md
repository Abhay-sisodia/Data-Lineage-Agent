# Phase 0 Tracker — Prove the Core

**Timebox:** 3 weeks (+ ~2 days week 0) · **Team:** 1–2 engineers · **Dialect:** Oracle PL/SQL
**Status:** Not started · **Created:** 2026-09-05

---

## Objective

**Determine whether column-level lineage through real procedural PL/SQL is accurate enough to stand behind.** Nothing else in the plan matters until that is answered.

The output of Phase 0 is **a number, not software**. Build two things only — an analyser and a scoring harness. No database, no API, no UI, no Docker, no agents.

**What exists at the end:** an analyser covering set-based SQL and most of the procedural core, a hand-labelled ground-truth corpus, a scoring harness, and a v0 IR derived from what the code actually contained.

**The gate:** band-1 precision **≥ 95%**, recall **≥ 85%**, scored per band against ground truth, with every unresolvable construct detected rather than guessed.

> **On the two thresholds.** The spike doc sets **≥ 98% precision as the target**; the build plan sets **≥ 95% as the gate**. Treat 98% as what we aim at and 95% as the floor below which the regulatory positioning is dead. Anything landing between them is a conversation, not an automatic pass.

---

## Standing rules for the phase

- **Score per band, always.** A single blended number will hide that band 0 is perfect and band 1 is broken — which is the only thing we actually want to learn.
- **Read the result as a floor, not a forecast.** Real legacy code is consistently worse than anything we would write on purpose.
- **Never emit a guessed edge.** Abstention is a deliverable, not a failure mode.

**Notes carried forward:**

- **The plan's third-party sources do not deliver Oracle PL/SQL.** Apache OFBiz is Java
  plus entity-engine XML; ERPNext is Python on MariaDB. Neither contains the procedural
  Oracle code this spike exists to test. Better candidates, all permissively licensed
  and genuinely Oracle: **utPLSQL**, the **Alexandria PL/SQL Utility Library**, **Oracle
  Logger**, and **Oracle's db-sample-schemas**. This is a substitution against the plan
  and needs a decision before fetching.

- **The ground-truth package is provisional and known-inadequate on its own.**
  `b1_07_package_variables.sql` yields only a handful of edges, and a precision figure
  over a handful of edges is not defensible. Synthetic code is also consistently cleaner
  than real legacy code, so any score against this corpus is a **ceiling, not a
  forecast**. One sanitised real production package remains the highest-value
  outstanding item, and it has human latency that cannot be compressed.

- **Compiling the corpus caught a design error that parsing did not.** The first
  `s5_positional_union` reversed column types as well as names, so Oracle rejected it —
  making it a *loud* failure and testing nothing. A silent failure must compile, run and
  produce plausible output, with only the lineage wrong. Rewritten so types line up
  positionally while aliases disagree. **Parsing is not evidence that a corpus is real.**

- **GL-001** logged in `docs/grammar_limitations.md`: the grammar rejects ANSI
  `DATE 'yyyy-mm-dd'` literals in partition bounds, though Oracle accepts them.

> **Critical path note.** The Oracle XE instance is required for T3.3, not just convenience — without a customer we have no query log, so we must execute the corpus ourselves to generate one. If that does not produce realistic `MODULE` / `ACTION` attribution, we need to know in week 0, not week 3.

## Week 1 · Baseline and harness

### T1.1 — Ground-truth label format

- [x] Six scoring decisions recorded — `docs/decisions/0001-scoring-model.md`
- [x] Schema implemented — `src/lineage/harness/labels.py`
- [x] Validator + 11 tests pinning each decision — `tests/test_labels.py`

**Done when:** the format is written down and a validator rejects a label row missing any required field.

**Status: CLOSED.**

**The six decisions (ADR-0001):**
1. Database is the referee — labels anchored by execution, not by reading code
2. Filter influence is an edge, scored separately from value flow
3. Variables are first-class nodes — def-use scored hop by hop
4. Wrong transform class = MISS (edge identity is `source, target, flow, transform`)
5. Guards excluded from precision, reported separately
6. Edge band = hardest construct on its path

Net effect: stricter scoring, lower number, more defensible. **The 95% gate applies to
band-1 value-flow precision** and must be stated wherever the figure appears.

### T1.2 — Hand-label ground truth for one package ← *the step everyone skips*

- [ ] Label every target column in the ground-truth package
- [ ] Second independent pass
- [ ] Adjudicate and record all disagreements
- [ ] Freeze and hash the label file

**Done when:** every target column has its true source columns labelled; the second pass agrees on ≥ 95% of edges with all disagreements adjudicated and recorded; the label file is frozen and hashed; labelling time is recorded so we can cost future corpus growth.

> Do this in week 1, **before** we are invested in the analyser being good. Without it we have opinions instead of a measurement.

### T1.3 — Scoring harness

- [x] Tier + mechanism distribution reporting
- [x] Guard accuracy reported separately from precision
- [x] Boundary declaration scored (undeclared known-unknowns are reported)
- [x] Label provenance (observed / adjudicated / source_read) printed with every score

**Done when:** it reproduces hand-computed precision/recall exactly on a small fixture with known answers; a single command produces the full report; two runs on identical inputs give byte-identical output; the report records corpus hash and code commit.

**Status: CLOSED except parse coverage**, which cannot be measured before an analyser
exists to refuse anything. Carried into T1.5.

- `tests/test_scoring.py::test_matches_hand_computed_scores` — a fixture worked out by
  hand, so the harness is verified against arithmetic rather than against itself
- Single command: `lineage score ground_truth/<file>.yaml [--predictions out.json]`
- Determinism asserted by test; no timestamps, all ordering sorted
- Source hash verified before scoring — refuses to score a key that has drifted from
  the code it describes

**The gate is named in the report itself:** `GATE (band 1, value flow)` with its 95% /
85% thresholds, so no other figure can be mistaken for it.

**Baseline recorded** — empty prediction set against b1_07: recall 0.0%, 8 edges missed.
Every future run is measured against a real starting point rather than an impression.

### T1.4 — Schema binding and dictionary name resolution at ingest

- [x] Resolve synonyms against `ALL_SYNONYMS` / `ALL_OBJECTS`, with cycle protection
- [x] Bind unqualified names per execution schema, recording which schema resolved them
- [x] Identify views and capture their text for base-table resolution
- [x] Expand `SELECT *` against DDL, following synonyms
- [x] Dictionary captured as a fingerprinted, committed snapshot

**Done when:** the synonym-redirect adversarial package resolves to the true underlying object, not the literal name in code; `SELECT *` expands correctly against DDL; the resolution itself is stored as evidence on the edge; a deliberately stale DDL snapshot produces a detected mismatch rather than a silently wrong expansion.

**Status: CLOSED.** All four conditions verified by test.

- `customer_target` resolves to `LINEAGE.DW_DIM_CUSTOMER_V2` — silent failure **s1**
  defended, and the test asserts the literal name does *not* survive
- Every resolution carries its chain in `via` — evidence, not an assertion
- **`SELECT *` against an unknown object raises rather than returning `[]`.** Returning an
  empty list would silently drop every column of something we could not see, producing a
  confident wrong answer with no symptom. That is the stale-DDL failure mode.
- Dictionary fingerprint excludes capture time, so an unchanged schema fingerprints
  identically and the pinning check does not fire on every run and get ignored as noise
- Synonym cycles terminate rather than hanging

**Carried forward:** view → base-table *resolution* still needs the view text parsed
(silent failure s6). The text is captured; expansion lands with the analyser in T1.5/week 2.

> This single step kills three of the eight silent failures and is the highest-value defensive move in the engine.

|---|---|

Locked in by `tests/test_band0.py` — 16 tests, run on every build. Ground truth for all

**Band 0 works. The spike continues to band 1.**

**Notes carried forward:**

- **Trigger edges are labelled band 2, not band 0** (ADR-0001 §6). This is doing real
  work: `trg_recent_audit` writes `DIM_CUSTOMER.LIFETIME_VALUE` on every insert into
  `tmp_recent`, and if those edges scored as band 0 they would drag band-0 recall down
  for a construct the band-0 analyser is not meant to handle. They currently score 0% in
  band 2, correctly.
- **Two limits of observation found, one fixed.** Set-based diffing reported "no change"
  for a real write whose values already existed — fixed by counting occurrences.
  Idempotent writes (`b0_merge` setting values already present) remain invisible *in
  principle*; that package's labels are all `source_read` and the evidence split says so
  on every score.
- **Join conditions are deliberately not filter edges.** `ON d.cust_id = s.cust_id` is
  structural, not row-selection policy. Treating join keys as filter lineage would flood
  every multi-table statement with edges that tell a reader nothing. Applied consistently
  in the analyser and the answer key.
- **`COUNT(*)` produces no edge.** A row count has no source column; inventing one would
  be a false edge.

## Week 2 · The procedural core

### T2.1 — IR v0 implementation

- [ ] Nodes: Column, Relation, Variable, Procedure, Statement, Boundary
- [ ] Edges: `derives_from`, `writes`, `reads`, `calls`, `contains`
- [ ] Edge attributes: transform, guard, origin, mechanism, tier, valid_time, tx_time
- [ ] Supersession semantics — never update an edge

**Done when:** a schema validator rejects any edge missing origin or mechanism; guard is the only nullable attribute; serialisation round-trips losslessly; an update attempt closes the old validity interval and appends rather than mutating.

### T2.2 — CFG construction

- [ ] Branches, loops, cursors
- [ ] Exception handlers as CFG edges, tagged exceptional

**Done when:** CFGs for the adversarial packages match hand-drawn expected node and edge counts; exception handlers appear as CFG edges; construction terminates on the deepest procedure in the corpus.

> An error path may write somewhere the happy path never does.

### T2.3 — Def-use chains over variables and temp tables

- [ ] Variables and temp tables treated as memory locations

**Done when:** the `refresh_active_flag` worked example produces exactly the documented edges e1–e5 with the right mechanisms; variable-carried edges are scored as their own category in the harness.

### T2.4 — Branch guards on edges

- [ ] Guard condition attached to every conditional edge

**Done when:** the EU-guarded edge carries `p_region = 'EU'`; unconditional edges carry null; a nested-IF adversarial case produces the correct conjoined guard.

> An edge that only fires for EU customers is a different fact from an unconditional one, and a regulator will ask about precisely that.

### T2.5 — Temp and global temp tables as first-class relations

- [ ] Scope by (procedure, session), never by name alone

**Done when:** the adversarial package where two unrelated procedures both write `tmp_recent` produces **zero** fused cross-procedure edges.

> This is a silent failure — it needs its own explicit test, not incidental coverage.

### T2.6 — Loops and fixed-point iteration

- [ ] Fixed-point iteration to a stable edge set
- [ ] Documented iteration cap

**Done when:** every loop in the corpus reaches a stable edge set within the documented cap; termination is proven, not observed once.

### T2.7 — Interprocedural summaries, depth-capped

- [ ] Summarise each callee once, inline the summary
- [ ] Depth cap as a config value
- [ ] Boundary node beyond the cap

**Done when:** a nested call chain resolves to the configured depth; beyond the cap a boundary node is emitted and counted, never a guessed edge; the cap appears in the output report; a recursive package terminates.

### T2.8 — First real band-1 precision number

- [ ] Full harness run

**Done when:** the run produces per-band precision, recall, parse coverage and tier distribution, recorded against the corpus hash and commit.

> Mid-point checkpoint — if band 1 is broken, we know in week 2.

## Week 3 · Undecidables and the verdict

### T3.1 — Unanalysable-construct classifier

- [ ] Detect and declare every construct the analyser cannot resolve

**Done when:** 100% of injected known-unresolvable constructs are flagged; **zero** edges exist for any statement the classifier flagged — verified by cross-checking flags against emitted edges, not by inspection; the false-abstention rate is measured and reported.

> The classifier that says "I cannot resolve this" is itself a deliverable.

### T3.2 — Dynamic SQL, constant string

- [ ] Constant propagation through the CFG, then parse normally

**Done when:** the constant-string adversarial package produces edges at mechanism `AST`, indistinguishable from static SQL.

> Cheap win — do this before reaching for the log.

### T3.3 — Query-log recovery sub-spike

*Start in parallel from the beginning of week 2, not sequentially.*

- [ ] Attribution via `MODULE` / `ACTION` session attributes
- [ ] Timing correlation against job-run windows
- [ ] Statement-shape matching against literal fragments in code
- [ ] Schema / user fallback
- [ ] Truncation detection
- [ ] Bind-variable structural assumption check

**Done when:** we have a measured number for what fraction of dynamic statements can be attributed to an emitter with high confidence (**below ~60% the compliance coverage story gets uncomfortable**); attribution signals are ranked by measured strength; truncation is detected and the edge marked partial; the assumption that bind variables hide values but not structure is confirmed, including the table-name-position case that would break it.

> Highest-leverage idea in the architecture and the one most likely to fail quietly. Test it early, on its own.

### T3.4 — Silent-failure adversarial suite

One small package each:

- [ ] Synonym redirect
- [ ] Schema context / unqualified name resolution
- [ ] Shared temp tables across procedures
- [ ] Partition exchange (DDL as lineage-bearing)
- [ ] Positional `UNION` binding
- [ ] Updatable views / `INSTEAD OF` triggers
- [ ] Unexercised branches
- [ ] Aggregation vs. row-level transform class

**Done when:** every case either passes or its failure is explicitly declared in the report; each becomes a permanent regression test the day it is written.

> Build the corpus around the *silent* list — loud failures announce themselves during testing. Silent ones surface when a customer catches you.

### T3.5 — `unexercised` as a first-class edge state

- [ ] Model it as a separate axis from tier

**Done when:** an edge can be Tier A *and* never observed running; the harness reports the count.

> That combination is itself a finding, and nobody else reports it.

### T3.6 — Full scoring run

- [ ] Precision, recall, parse coverage per band
- [ ] Honest-abstention check as pass/fail
- [ ] Tier distribution examined explicitly

**Done when:** all of the above are reported per band. If 70% of edges land in Tier C or D, the lineage technically works but the evidence story doesn't — flag it.

### T3.7 — IR v0 written down

- [ ] Schema documented as a straw-man to argue with
- [ ] Rationale for keeping `mechanism` and `tier` separate
- [ ] Every deviation from the draft schema explained by something the corpus actually contained

**Done when:** the document exists and each deviation is justified by real code, not preference.

### T3.8 — Go / no-go against the kill criteria

Written down before the work started, so the result is a measurement rather than an argument.

| Kill criterion | Measured | Verdict |
|---|---|---|
| Band-1 precision < 95% → regulatory positioning dead; engine still sells migration triage and dead-code detection, different buyer and pitch | | |
| Parse coverage < 70% on real code → parser strategy is wrong, not the idea | | |
| Dynamic SQL > 30% of statements **and** unrecoverable → coverage too thin for compliance work | | |
| Interprocedural analysis doesn't terminate at a usable depth → architecture needs rethinking before scale-up | | |

**Done when:** each criterion has a measured number beside it and a signed one-page verdict exists.
