## 3. The obstacle: why each blind holdout misses the bar

```
grammar checklist 99.8%  ──measures──►  one construct, one statement, in isolation
                                          │
blind holdouts fail on ─────────────────► PL/pgSQL semantics, the psql layer, and how
                                          statements and files combine - none of which
                                          the checklist has rows for
```

1. **The checklist measures the wrong level.** It is generated from pglast node types: one
   row and one simple snippet per construct. PL/pgSQL gets one row per statement *type*.
   Holdout4's causes have 0 rows: RETURN QUERY EXECUTE of folded text, an OUT-param
   function as a row source, RETURN NEXT of a record built field by field, BEGIN ATOMIC,
   `NEW.x :=` from a lookup, COPY FROM STDIN data, `\gset` / `:var`.
2. **We fixed what each holdout showed us** (reactive). Each fix holds (holdout1 and holdout3
   numbers above never regressed), but every new blind holdout brings ~6-9 new forms.
3. **The briefs got harder each round.** Holdout4's brief roughly doubled the PL/pgSQL and
   cross-file requirements (written by us), so blind numbers across holdouts are not a trend.
4. **One break cascades.** Entries are 4+ hops deep and share upstream: one COPY STDIN break
   and one `\gset` break each cost filters in ~10 of 16 entries; one missing node cost ~10
   points.
5. **The weak part is the PL/pgSQL *semantic* layer, not the parser** - measured, not assumed:
   across all 83 routines in every corpus, our hand-written reader (`parsing/plpgsql.py`)
   reads 83/83 and places statements on the same lines as PostgreSQL's own
   `parse_plpgsql` in 66/67 routines; it fails on exactly one statement form. What loses
   lineage is `analysis/plpgsql.py`: what a routine does with values.

**Research (2026-10-16): nothing open-source can replace either layer.**

- Parsing: pglast `parse_plpgsql` (already a dependency) is the only better parser, and our
  reader already matches it. Option "A" (rebuild the reader on it) was measured to buy
  little; use pglast only where it removes a text heuristic (INTO / RETURNING targets,
  variable kinds, OUT params).
- Semantics: no open-source tool does column lineage through PL/pgSQL. sqllineage,
  SQLGlot, DataHub, LineageX: single queries only. OpenMetadata: runtime query-log
  lineage (`pg_stat_statements`, lossy). python_data_lineage wraps Gudu's commercial Java
  engine (free for non-commercial use only). Dataedo / Gudu SQLFlow: commercial.
- Runtime oracle (PostgreSQL itself via `auto_explain` with `log_nested_statements` and
  `log_verbose`): the most accurate, but needs a real PostgreSQL 17 with contrib modules.
  Embedded `pgserver` (pip, no Docker or admin) works on Python 3.11 / Windows, but bundles
  PostgreSQL 16.2 without auto_explain. Docker here needed an org sign-in.

## 5. Proposed next steps (not started)

1. **Checklist v2 - a semantic matrix**, generated with known lineage: routine shapes
   (scalar / SETOF / TABLE / OUT-INOUT / record / BEGIN ATOMIC / LANGUAGE sql / RETURN NEXT /
   RETURN QUERY [EXECUTE] / loop-built rows) × call sites (SELECT list / FROM / LATERAL /
   named + VARIADIC args / inside another routine / a later file) × value paths (INTO,
   assignment, record field, OUT param, NEW/OLD, `\gset`, `:var`, COPY STDIN). Measured like
   `docs/pg-coverage.md`; finds holdout4-type gaps before a holdout does.
2. **Fix H1-H9** in the order above, driven by the matrix rows they fail.
3. **Freeze the brief** (`docs/holdout-brief.md`, the holdout4 brief) for holdout5, and re-run
   every holdout after each change (`scripts/holdout/run.sh`).
4. Later, optionally: a runtime oracle on a real PostgreSQL 17 with auto_explain.

## 6. Setting up on another machine

1. Clone, `git checkout kg-agent`. Python 3.11 venv;
   `pip install -r requirements.txt -r requirements-dev.txt` (hash-pinned; see README).
2. **Generate the ANTLR parser** (untracked): `python scripts/generate_parser.py` (needs Java).
3. **Neo4j:** tests and holdout runs use a **scratch** instance at `bolt://localhost:17687`.
   The dev graph at 7687 holds the user's own SQL - never point tests at it.
   `scripts/holdout/run.sh` refuses 7687.
4. **Holdout folders are NOT in the repo.** Copy `devin_fip 1/holdout`, `holdout3`, `holdout4`
   (each: schema/, seed/, sql/, expectations.md, GRAMMAR.md) to the new machine.
5. Full suite: `NEO4J_URI=bolt://localhost:17687 python -m pytest -q` (2285 passed, 2 skipped
   at 53cfb13; ~8-11 min).
6. One holdout, end to end:
   `NEO4J_URI=bolt://localhost:17687 bash scripts/holdout/run.sh "<path>/holdout4"`.

## 7. Working conventions (kept on the old machine's memory - restated here)

- Answers: short, specific pointers; an ASCII flowchart when discussing a complex problem.
- Commit and push only after explicit approval.
- PostgreSQL first; Spark / Databricks out of focus. Avoid LLM calls in the pipeline.
- Neo4j tests on the scratch instance only (17687).
- Keyed SQL must stay LF: Python `write_text` on Windows writes CRLF and breaks key hashes
  on a clean checkout - pass `newline="\n"`.
- On Windows Git Bash, heredocs and `sed` corrupt `\n` / `\b` in code: edit with the editor
  tools or a `.py` patch file.
- Measuring "before" vs "after": a `git worktree` at the old commit plus a copy of the
  generated parser, run from inside it (`scripts/holdout/replay.sh`). PYTHONPATH silently
  measures the working tree.
- Never `ruff format` `src/lineage/analysis/band0.py` (it reformats unrelated code).
